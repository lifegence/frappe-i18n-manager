## 1. ロケールの一覧（3 分）

`/app/locale-profile`

| ロケール | 国 | 言語 | 通貨 | 日付形式 | 数値形式 |
|---|---|---|---|---|---|
| ja-JP | 日本 | ja | JPY | yyyy-mm-dd | #,###.## / 小数 0 桁 |
| zh-TW | 台湾 | zh-TW | TWD | yyyy-mm-dd | #,###.## |
| zh-HK | 香港 | zh-HK | HKD | dd/mm/yyyy | #,###.## |
| hr-HR | クロアチア | hr | EUR | dd.mm.yyyy | **#.###,##** |

**話す点**

- **通貨と小数桁は言語では決まりません。** 円は補助単位を持たないので小数 0 桁、ユーロは 2 桁です。ロケールごとに持たせているのはこのためです。
- **クロアチアの通貨は EUR です。** 2023年1月1日にクーナから切り替わっています。国を追加するときに古い通貨を選んでしまう類の間違いを、レコードとして固定します。
- **数値形式が国によって逆になります。** クロアチアは小数点がカンマ、桁区切りがピリオドです。
- **香港のフォールバック先は台湾です。** Frappe は `zh-HK` の訳が無いとき自動的に `zh`（簡体字）へ落とします。香港で必要なのは繁体字なので、この経路は Frappe の既定では正しくありません。フォールバック先を明示的に持っているのはこのためです。

## 2. 測定（5 分）

ロケールを開き **「走査を実行」**。バックグラウンドで実行され、完了すると画面が更新されます（4 アプリで 25 秒程度）。

`/app/query-report/Localization Coverage` で全ロケールを横に並べます。

実測値（導入済み 23 アプリ、計 22,526 文字列）：

| ロケール | 表示上の網羅率 | 固有訳の網羅率 | 未訳 |
|---|---:|---:|---:|
| ja-JP | 88.4% | 88.4% | 2,607 |
| hr-HR | 73.4% | 73.4% | 6,001 |
| zh-TW | 71.7% | **13.9%** | 6,381 |
| zh-HK | 71.7% | **13.9%** | 6,380 |

**中国語圏で見せる場所です。**表示上は 71.7% ですが、そのうち約 13,000 件は簡体字からの継承です。繁体字圏として使えるのは 13.9% にすぎません。標準機能にはこの区別がなく、88.9% しか見えません。

**話す点 — ここがこのアプリの理由です。**

> 標準のしくみ（訳の置き場所 3 か所、解決の順序、親言語フォールバック、完全一致のキー）を先に説明すると理解が早くなります。利用マニュアル第 2 章にまとめてあります。

経路別に見ると値がまったく違います。

| 経路 | ja-JP の網羅率 |
|---|---:|
| ソースコード（frappe） | 96.5% |
| ソースコード（erpnext） | 98.4% |
| **データベース（erpnext）** | **13.6%** |
| **データベース（hrms）** | **4.4%** |

`bench get-untranslated` が見るのは **ソースコードだけ** です。標準機能だけで測ると「98% 完了」に見えますが、画面に出る文字のうちデータベースに入っているもの（オンボーディング、ワークスペース、レポート名、通知の件名）は **一件も数えられていません**。

フェーズ 1 でオンボーディング画面が英語のまま残っていたのは、この構造によるものです。

## 3. 指摘（5 分）

`/app/translation-issue` — ロケールで絞り込みます。

ja-JP の実測（5,312 件）：

| 種別 | 件数 | 意味 |
|---|---:|---|
| Untranslated | 2,607 | 訳が無い |
| Latin Residue | 1,644 | 訳文に英字が残っている |
| Not Wrapped | 468 | **翻訳関数を通していない** |
| Glossary Violation | 344 | 用語集と違う訳語 |
| Forbidden Term | 156 | 使用しないと決めた訳語が入っている |
| Whitespace Mismatch | 91 | 前後の空白が原文と違う |
| HTML Mismatch / Placeholder Mismatch | 各 1 | タグ・プレースホルダの欠落 |

**開いて見せる例**

- `Role Permission for Page and Report` → `Role Permission for Page andレポート`
  半分だけ訳された文字列。目視でしか見つからなかった類のものです。
- `Not Wrapped` の 1 件
  `frappe.throw("…")` に文字列が直接渡されています。**これは訳が足りないのではなく、翻訳ファイルが届かない場所にある**という指摘です。ソース修正が要ります。日本語化の作業だけでは絶対に解決しません。
- `Whitespace Mismatch`
  Frappe は原文を完全一致で引きます。末尾に空白がある文字列は別のキーです。フェーズ 1 で訳が効かず原因究明に時間を要した事象がこれです。

**ラテン文字の扱いは言語で切り替わります。** クロアチア語はラテン文字を使うので、`Latin Residue` 検査は自動的に無効になります（ロケールの「ラテン文字を使う言語」が判定します）。全ロケールに同じ検査をかけると、クロアチア語は全行が指摘されて使いものになりません。

## 4. 用語集と一括変更（5 分）

`/app/glossary-term` — ロケールごとに用語を持ちます。

日本語の例：`Item → 品目` / `Customer → 得意先`（**使用しない訳語：顧客**）/ `Acme → 訳さない`

ロケールを開き **「操作 → 用語の一括変更」**。

デモ：`在庫伝票` → `在庫エントリ`

1. 「影響範囲を確認」を押すと、変更対象が **実行前に** 一覧で出ます（19 件）
2. 「実行する」で確定
3. 再走査すると Glossary Violation が減ります

**話す点。** 用語集を変えると何件動くのかが先に見えます。フェーズ 1 では 3 回の一括置換をスクリプトで行いましたが、影響範囲はその都度手で数えていました。

---

## 4-2. 香港に繁体字を出す（5 分）

**Frappe 単体では香港は簡体字になります。** `zh-HK` に訳が無いと親言語 `zh`（簡体字）へ落ちるためで、`zh-TW` は親ではなく兄弟なので Frappe が自力でそちらを見ることはありません。

1. `zh-HK` のフォールバック先が `zh-TW` であることを見せる
2. **台湾 → 香港の順**で走査する（香港は台湾の台帳を読むため）
3. 走査ログの `Fallback : N taken from zh-TW` を見せる
4. 翻訳台帳で `Item` を開く — 訳文 **項目**、現在の表示 **物料**
5. 「操作 → サイトへ反映」
6. 表示言語を香港にして品目一覧を開く — **項目 / 項目名稱 / 啟用**（繁体字）

**手順 4 と 5 の区別を必ず説明してください。**台帳に訳があることと、画面に出ることは別です。反映操作を経なければ画面は変わりません。

## 5. 成果物の書き出し（3 分）

ロケールの **「書き出す」** から：

- **レビュー表 (CSV)** — 「修正案」「確認者コメント」の記入欄付き。貴社にお送りして戻していただく想定です
- **アプリ同梱 CSV** — `<app>/translations/<lang>.csv` そのものの形式。本社リポジトリにそのまま置けます

**「操作 → サイトへ反映」** で、承認済みの訳を `Translation` レコードとして実機に書き込みます。Frappe の解決順序ではこれが最優先なので、アプリ同梱の訳を上書きできます。

反映結果は実際に画面に出ます（上の一括変更を反映すると、在庫関連のメッセージが「在庫エントリ」に変わります）。

## 6. 国を後から追加する（5 分）

**ここが本題です。** 4 か国は初期セットであって、固定ではありません。

`/app/locale-profile/new` で 4 つ入れるだけです。

| 項目 | 値 |
|---|---|
| ロケールコード | ko-KR |
| 国 | Korea, Republic of |
| 言語 | ko |
| 通貨 | KRW |

保存すると自動で：

- `Language` レコードが無ければ作成し、無効なら有効化します
- `Currency` が無効なら有効化します（KRW は既定で無効です）
- 言語コードからラテン文字かどうかを判定します
- 国からタイムゾーンを引きます

**「走査を実行」** すると、同じ 18,142 文字列に対して **網羅率 0%** と出ます。韓国語の訳は同梱されていないので、これが正しい出発点です。何をどれだけ訳す必要があるかが、初日に数字で出ます。

> 香港（zh-HK）は Frappe に存在しない言語コードでした。このアプリが `Language` レコードを作っています。標準では「言語が見つからない」で保存できません。

## 6-2. アプリ自身も多言語です（2 分）

表示言語を日本語 → 香港に切り替えて、同じロケール画面を見せます。

- 日本語：表示名 / フォールバック先 / 走査を実行
- 香港：`Locale Name` / `Fallback Locale` / `Run Scan`

**原文は英語で、日本語は `translations/ja.csv` で当てています。** 未対応の言語では原文（英語）が出ます。日本語のまま残るということはありません。

**同梱する語は選んでいます。** `Status` や `Draft` のような一般語を入れると ERPNext 全体の日本語表示を書き換えてしまうため、frappe / erpnext がすでに訳している 56 語はそちらに委ねました。**核となる訳をアプリから上書きしない**という原則は、このアプリが検出する問題そのものです。

## 6-3. 後から入れたアプリも対象になる（3 分）

**対象アプリが空であれば、次回の走査から自動で入ります。** 設定変更は要りません。

この環境で対象を 4 アプリから全 23 アプリへ広げると、台帳が **4,376 件増え**、それまで見えていなかったアプリの実態が出ます。

| アプリ | 総数 | 網羅率 |
|---|---:|---:|
| clefincode_chat | 506 | 0.2% |
| wiki | 300 | 0.3% |
| lifegence_customization | 92 | 0.0% |

**対象アプリを明示している場合は要注意です。** 後から入れたアプリは対象外のままになるため、走査ログに `NOT MEASURED (19): ...` として毎回列挙します。網羅率が高いままアプリ 1 本まるごと未訳、という状態を黙って作らないためです。

## 7. 継続測定

`hooks.py` で毎週の自動走査を登録しています。有効なロケール全件を走査し、増えた未訳を一覧化します。

**本社の開発が続く限り、新しい文字列は増え続けます。** 一度測って終わりではなく、数字が動き続けるという前提の作りです。

## 現時点で入っていないもの

- **実画面の自動巡回（提案書の段階 4）。** ブラウザを操作して実際に描画された文字を拾う機能は未実装です。提案書どおり、方式検証を経てから判断する範囲としています。
- **機械翻訳の実行。** 台帳と検出の仕組みであり、訳す機能ではありません。
- **帳票（APITemplate）の多言語化。** 外部サービス側の対応が必要です。

## 正直に申し上げる点

`Latin Residue` は件数が多く（ja-JP で 1,644 件）、そのままでは使えません。ブランド名・単位・略号を「英字のまま許容する語」に登録して減らしていく運用が要ります。**指摘一覧であって、エラー一覧ではありません。**

実画面の確認を完全に代替するものでもありません。値打ちは「確認を不要にすること」ではなく、**確認すべき箇所を絞り込み、見落としの母数を減らすこと**にあります。
