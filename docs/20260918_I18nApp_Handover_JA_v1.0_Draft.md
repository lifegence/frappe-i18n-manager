## 2. 設計上の判断（理由付き）

### 2-1. 「見た目」ではなく「置かれている場所」で判定する

画面の文字が「翻訳すべき UI 文字」か「顧客のデータ」かは、文字の見た目では分からない（Bath Bomb Sea Salt は商品名、Quick Access は見出し）。そこで **DOM 上の位置**で決める。値の領域（`.control-value`、一覧の行、グリッドの行、ツリーのノード、グラフ、タイムライン、コードエディタ、DocType 編集画面のフォームビルダ）にある文字は全部データ扱い。これらの CSS クラスは v15 と v16 で同じだった。

加えて「サイト自身が持つ値」を使う: ページ上の入力値、URL のレコード名、マスタ 19 種のレコード名、導入済みアプリ名、ログイン中ユーザーの氏名。環境固有の辞書には頼らない。

### 2-2. テキストの単位は「インライン要素の連続」

Frappe はボタンのアクセスキー 1 文字を別の `<span>` に入れるため、テキストノード単位だと「A」「sset Capitalization」に割れる。逆に `<a>` を全部つなぐとリンク一覧が 1 文になる。妥協点として「親要素に地の文があるときだけ結合」。`COLLECT_JS` の `hasDirectText`。

### 2-3. 台帳との照合は多段

そのまま → 空白・実体参照の正規化 → 記号除去 → 数値・括弧をプレースホルダに → 型（正規表現）。型は「プレースホルダだけ（"{0}"）」だと何にでも一致するので、**文字が 2 語以上・8 文字以上**の型だけ無条件に使い、短い型（"Add {0}"）は中身が既知の原文か値のときだけ一致させる。この不具合は検証中に実際に起き、「翻訳あり・画面は英語」を 5 倍に水増ししていた。

### 2-4. 「日本語が含まれていれば翻訳済み」だが、型だけ未訳は拾う

「Show アイテム List」は値が訳されて型が未訳。CJK を含む文字列は原則スキップしつつ、型照合で未訳の型に当たった場合だけ候補にする。

### 2-5. Playwright は任意依存

Frappe Cloud にはシェルが無く Playwright を入れられない。`is_available()` が偽なら走査は「Screen: skipped」と記録して他の経路を続ける。別マシンからは `bench execute lifegence_i18n.scanner.screen.run` で画面巡回だけを回す。

### 2-6. 巡回順は独自アプリ優先、上限は設定（0 で無制限）

管理者の画面は約 2,000（DocType 約 650 × 一覧・新規・既存 1 件）。上限に達したとき「他の経路が見ていない画面」が回られているべきなので、frappe・erpnext は最後。順番はワークスペース → Single 設定 → DocType 名前順。**利用者が画面で作った公開ワークスペースは module が無く `site` 扱いで、どのアプリよりも先に回る**（サイト固有のものは巡回でしか測れないため）。したがって先頭が自アプリのワークスペースとは限らない。テストはこの前提で「対象アプリの画面の中での順」を見る（PM 指摘 9/24、野村さんのベンチで先頭が手作りワークスペースになりテストが落ちた）。custom=1 の DocType も所属モジュールのアプリとして含む。上限は I18n Settings（既定 300、0 で無制限）。裏側の処理の打ち切り時間は上限から算出する（4 秒×画面数＋30 分、最低 2 時間）。

### 2-7. 件数入りの文字列は型の形で保存する

「4 To Receive」を毎週別の行として登録しないよう、先頭の数値だけ `{0}` にして保存（`LEADING_COUNT`）。数値を全部置き換えると URL や「3 variables」まで壊れる（実際に壊した）。

### 2-8. 略号は候補として残し、未訳に数え続ける

全大文字の単独トークン（SKU、FAX、DESC）は既定の除外規則「Acronym」（自動適用オフ）が理由「略号・コード」を付ける。状態は未訳のままで、S-6 で人が確認する。当初は画面巡回だけで特別扱いしていたが、PM 判断 3-2(b) と受入試験の型（README 2 章）に合わせ、全経路で同じ規則にした。既存サイトには `v1_2/seed_acronym_rule` が規則を足す。

### 2-9. 「訳があるのに画面は英語」は「翻訳関数の未適用」の指摘にする

台帳に訳があり、ファイルにもあり、反映検証は Live なのに画面は英語、というものがある（`set_primary_action("Export")` が `__()` を通っていない等）。反映検証では見えないので、既存の指摘種別「Not Wrapped」に、詳細 `screen: <URL> (<要素>)` を付けて残す（PM 判断 3-1: 原因が同じなので種別は増やさない）。修正はコード側（上流）で必要。

**対象は「承認済みで、このサイトが現にその訳を解決している行」に限る。** 下書き・未反映・フォールバック由来の行は反映検証の領分。

### 2-10. アプリ自身の翻訳は、ほかのアプリの訳と食い違う行を入れない

翻訳はアプリの導入順にマージされ、後のアプリが勝つ。本アプリは最後に入ることが多いので、ほかのアプリがすでに訳している語に**別の訳**を ja.csv で持つと、その語の訳をサイト全体で書き換えてしまう。同じ訳を重ねて持つだけなら実害はない。

テスト `test_no_translation_that_differs_from_the_apps_already_in_effect` は、`frappe.translate.get_translations_from_apps("ja", apps=本アプリ以外の導入済みアプリ)` で「いま実際に効いている訳」を取り、ja.csv の各行と**値**で突き合わせる。version-15 の frappe 同梱の日本語でも、配布された日本語化アプリ（PM 側では frappe_japanese_translations、21,845 行）でも、同じ基準になる。比較対象がひとつも無いベンチでは skip ではなく失敗にする（PM 依頼 9/25。以前は frappe・erpnext の ja.csv をパスで読んで**キー**の一致を見ていたため、version-16 では skip になり、当方の環境で隠れていた）。

本アプリ固有の語感が欲しい語は、原文もアプリ固有にする。「Issue Summary → 指摘の要約」「Occurrences → 出現回数」は配布側の「課題サマリ」「発生回数」と食い違ったため、原文を `Finding Summary`・`Occurrence Count` に変えた。Database / Result / Source Code / Running は値が一致しているのでそのまま。Queued / Completed / Failed は frappe が訳しているので入れていない。

### 2-11. 画面で見つけた文字列にも除外規則を適用する

経路 4 の新規行も `utils.classify()` を通し、命名シリーズ等は理由付きの「対象外」として登録する（S-2 の「黙って捨てない」）。略号は 2-8 のとおり候補として登録する。

### 2-12. 用語集の「訳さない語」はブランド名の判定に使う

理由コード「ブランド・製品名」は台帳に定義だけあって、付ける仕組みが無かった。受入試験の型（README 2 章）のとおり、用語集で「訳さない」かつ「違反を指摘として記録する」の語に**原文全体が一致**する行を、`_upsert` が「対象外（ブランド・製品名、規則 `Glossary: <語>`）」として登録する。「Acme ERP Sync Status」のように語を含むだけの行は UI テキストのままで、訳に語が残っているかは用語集チェックが見る。

あわせて、後から追加した規則が「誰も判断していない行」（未訳で訳文なし）に次の走査で適用されるようにした。承認済みの行や人が訳を書いた行は、規則が理由を提案するだけで状態は変えない。

### 2-13. 反映検証の 4 状態は「ファイルにあるか」で切る

受入試験の型（README A-4）の定義に合わせた。承認した訳が**どのアプリのファイルにも無い**行は、画面に何が出ていても（古い訳、上流の訳）「未反映（Not Deployed）」。ファイルが解決する値と一致するのに画面が違えば「キャッシュ古い（Cache Stale）」、ただし Translation レコードがその原文を持っていれば「上書き（Overridden）」。どこかのアプリのファイルにはあるが後のファイルが勝つ行も「上書き」。以前は「画面に別の訳が出ていれば上書き」としていたため、訳文を変えた行が未反映ではなく上書きに数えられ、A-4 の「変更 5 行が Not Deployed」を満たせなかった。`_file_translations` は結合後の値と、アプリ別の値の集合の両方を返す。

### 2-14. version-16 のテストは `--test-category all` が要る

version-16 は単体テストと結合テストを分け、既定では単体だけを走らせる。`bench run-tests --app lifegence_i18n` は DB を触らないものだけで「OK」と出し、残りを黙って除外する。`--test-category all` を付けると結合と単体の 2 行が出て合計が揃う。version-15 は既定で全件走る。

### 2-15. 台帳との照合は 4 段構え

1. **そのまま**（前後の空白・記号を落とした形、実体参照を戻した形）
2. **値を戻した形**（数字・括弧・先頭の件数をプレースホルダへ。件数は「4」「0/4」「0%」「0 %」の 4 通り）
3. **型**（`You haven't created a {0} yet` のような、文字を含む型）
4. **まとめて訳される行の一部**（2-16）と、**マークアップを潰した形**

4 の「潰した形」は、`説明文。<br><br>注意：…` のように台帳にマークアップ付きで入っている行が、画面では 1 行に見えるため。公開アプリの検証では v15 で 5 件、v16 で 5 件がこれに当たっていた。

### 2-16. 描画されて分かれた文字は、元の 1 行に戻して照合する

DocType の説明文は Markdown、HTML 項目は HTML で、**Frappe はそれぞれを 1 つの翻訳対象文字列として扱う**。画面ではそれが見出し・段落・箇条書きに分かれて描画される。分かれた各行をそのまま新規の未訳として登録すると、(1) 1 つの未訳が 10 件に水増しされ、(2) その行だけを訳しても画面は変わらない（Frappe は分割後の文字列を知らない）。

`Ledger` は、改行か `<` を含む台帳の行から、Markdown の記号と HTML タグを外した各行を索引に持つ（`fragments()`）。画面の文字がその索引に当たれば「台帳にある行の一部」として確認済み扱いにする。索引に載せるのは 12 文字以上かつ 2 語以上の行だけ（短い語が本物の未訳を飲み込まないため）。

公開アプリの巡回で、ERPNext の導入案内（Onboarding Step の description）1 件から 20 件の「新規未訳」が出たのが発見の経緯。誤検出率は 3.6% ではなく 79% だった。

### 2-17. 開けない画面は「見た」に数えない

巡回用ユーザーが読めない DocType の画面を開くと、version-15 の Frappe は**デスクを空のまま、ダイアログで「見つかりません」を出す**（`.message-page` ではなく `.msgprint` のモーダル）。当初はこれを普通の画面として読んでいたため、ナビゲーションバーとダイアログの文字を「その画面の文字」として集め、見ていない画面を「見た」に数えていた。

`.page-container` / `.page-head` / `.layout-main-section` のいずれも無ければ「巡回用ユーザーには開けない画面」として失敗に数え、走査ログに理由別の件数を出す。公開アプリの検証では、閲覧専用ユーザーで 400 画面中 324 画面がこれに当たっていた（ERPNext と hrms の DocType を読む権限が無かった）。

あわせて、通信が静かになるのを待つ上限を 15 秒から 4 秒に下げた。開発用サイトは socket.io の再接続を繰り返すため通信が止まらず、1 画面あたり 17 秒かかっていた。

### 2-18. 経路 2 は「この版に無い列」を黙って捨てていた（既存不具合）

`database.py` の対象表は DocType ごとに読む項目を固定している。version-16 の `Module Onboarding` には `subtitle` も `success_message` も無く、問い合わせが失敗して `except: continue` で**その DocType 全体を無言で除外**していた。`title` 9 件（各モジュールの導入案内の題名）が測定から丸ごと落ちていた。

実在する列だけを読み、落とした列があれば走査ログに 1 行残すようにした。公開アプリの巡回が「経路 2 が知らないはずのない文字列」を見つけたことが発見の経緯。

### 2-19. 子テーブルの行は親のアプリに帰属させる（PM 回答 別紙 2、9/20）

Workspace の Link / Shortcut / Number Card / Chart / Quick List と、version-16 の Workspace Sidebar Item は子テーブルで、module 項目を持たない。以前は一律に `site` に帰属させていたため、顧客アプリのワークスペースのリンク（ある案件で 109 件）がそのアプリのエクスポートから漏れていた。`database.collect()` は子テーブルの行を `parenttype` の表から親の module を引いてアプリに帰属させる。親が利用者の手作りでモジュールが無ければ従来どおり `site`。

**既存行の扱い**: `_upsert` は原則として既存行の app を変えない（最初に見つけたアプリが持ち主）。ただし `site` は「持ち主不明」の仮置きなので、走査が実アプリを特定できたときだけ `site` → 実アプリに書き換える。実アプリ同士の付け替えはしない。書き換えた件数はアプリごとに走査ログの `Claimed from site: 109 (acme_erp 87, erpnext 22)` の行に残す（PM 依頼 9/22。顧客の台帳では 1 回の走査で 100 件超が動くため、あとから追えるようにする）。

### 2-20. version-16 のワークスペース側枠（Workspace Sidebar）

version-16 は側枠を `Workspace Sidebar`（title、module）と子テーブル `Workspace Sidebar Item`（label）で持つ。両方を経路 2 の対象に足した。version-15 には無い DocType なので、無い版では読まない（DocType の有無は黙って飛ばす。列の有無だけログに残す）。

番号カードとグラフの題名は Frappe が `base_widget.js` で `__()` に通している（両版とも 102 行目付近）。実画面でも、一時的に訳を置くと題名が訳されて出ることを確認した。したがって PM 回答 別紙 5 の条件③は「通している」が答えで、翻訳関数の未適用にはならない。

### 2-21. 既定の除外規則は 9 件（PM 回答 別紙 3）

`eval:` で始まる式、`/api/` で始まるパス、`#f5f5f5` のような色コードを Developer Note として自動適用で追加。既存サイトには `v1_2/seed_developer_note_rules` が足す。

### 2-22. 安全側の判断

- 同じロケールの走査が「待機中」「実行中」のうちは、新しい走査を始めない（`another_running`）。2 つの走査が同時に台帳へ書くと `_upsert` の一意キーで片方が落ちる（フィクスチャ検証中に実際に起きた）。15 分以上更新の無い「実行中」は落ちた走査の残骸とみなして無視する（`STALE_AFTER_MINUTES`。巡回中は 25 画面ごとに更新時刻を打つ）
- 巡回用ユーザーは閲覧専用を推奨。空欄なら Administrator（PM 判断 4-1）。System Manager は保存済みパスワードを読み出せるため、設定画面にその旨を明記
- 巡回先 URL は検証する（https、プライベートアドレス不可、他サイトは site_config の許可が必要）
- 巡回ユーザーの言語がロケールと違えば中断する。自サイトはブラウザを起動する前に DB で、他サイトはログイン後にデスクの boot（`frappe.boot.lang`）で確認する
- 巡回後にログアウトし、台帳・ログにはレコード名を残さない（レコード画面は `/app/<doctype>` までで記録）
- 初版はクリック操作をしない（メニュー・フィルタ・ダイアログは次版。PM 判断 2-5）
- 走査ログに、巡回した画面の一覧と、保存前に正規化した文字列を残す（PM 判断 3-3, 5-3）
- 翻訳台帳に (locale, text_hash) の一意制約。パッチ `v1_2/unique_ledger_rows` が重複を統合してから制約を追加（PM 判断 4-3）
- 「見つかりません／権限なし」の画面は DOM の構造で判定し、言語に依存しない
- api.py の全公開関数は System Manager 限定

### 2-23. 画面の判定は対象サイト自身の辞書で行う（PM 提案 9/22）

`screen.collect()` はログイン直後にデスクから `frappe.boot.__messages`（そのユーザーの言語の訳の全件。version-15、16 とも `boot.py` が呼ぶ `translate.get_messages_for_boot()` ＝ `get_all_translations(lang)`）と `frappe.boot.lang` を 1 回読み取り（`_site_dictionary`）、以後の判定の辞書にする。9/20 時点では巡回マシン側の `get_all_translations()` を使っていたため、別マシンから巡回すると両者の翻訳ファイルのずれがそのまま「翻訳関数の未適用」に数えられた（version-15 から日本語の無い version-16 を巡回して 8 画面 65 件）。

判定は `judge(row, served)` に 1 か所にまとめ、結果は 3 つ。(1) 対象サイトが訳を配っているのに画面は原文 → `NOT_WRAPPED`（翻訳関数の未適用。従来どおり指摘を起票）。(2) 台帳に承認済みの訳があるが対象サイトは配っていない → `NOT_DELIVERED`（新設。走査ログに件数と一覧を残すだけで、指摘は起票しない。反映検証はあくまで巡回マシンのファイルを見るため、別マシン巡回では対象サイトの反映状況はこの数字が唯一の手がかり）。(3) 台帳に訳が無い → `CONFIRMED`。下書きと対象外は判定しない。

同じサイトを巡回する通常の使い方では、boot の辞書はサイト自身の `get_all_translations()` と同じ関数の出力なので、結果は変更前と同一（version-15 の 400 画面で確認）。デスクが読めなかった場合だけ巡回マシンの辞書に戻し、その旨をログに残す。

### 2-24. version-15 互換の確認（WP-4 の観点、9/23）

PM が version-15 で見つけたワークスペースのアイコン欠落（`icon: globe` は version-16 のアイコンセットにしか無い。main 747e5ab で両版にある `text` に修正済み）を受けて、version-16 固有の名前を使っている箇所が他に無いか、本アプリの全ファイルを機械的に洗い出して両版のベンチで突き合わせた。

| 確認項目 | 洗い出し方 | 結果（version-15） |
|---|---|---|
| アイコン名 | 全 JSON の `icon` | `text` の 1 か所のみ（修正後）。両版にある |
| 参照している DocType 名（54 種） | Python の get_all / get_doc / db.* / SQL の tab 名、JSON の Link・Table の options、ワークスペースの link_to | version-15 に無いのは `Workspace Sidebar` と `Workspace Sidebar Item` の 2 種だけ。いずれも `database.collect()` が `frappe.db.exists("DocType", …)` と `table_exists` で無い版では読まない（2-20）。version-16 では 54 種すべて存在 |
| 項目の型（14 種） | 自作 DocType の JSON の fieldtype | すべて version-15 の DocField で使われている型 |
| Python から呼ぶ frappe の API（52 経路） | `frappe.` で始まる属性経路を両版で実際に解決 | 両版とも解決できる（`frappe.boot.__messages` / `frappe.boot.lang` の 2 つは JS 文字列内の名前で、Python の属性ではない） |
| JS から呼ぶ frappe の API（10 種） | 6 本の JS の `frappe.` 経路を version-15 の `frappe/public/js` で検索 | すべて存在 |
| hooks.py のキー（9 種） | version-15 の frappe が `get_hooks` で読む名前と照合 | すべて version-15 が読む（`add_to_apps_screen` を含む） |
| 画面の経路 | `/app`（v15）と `/desk`（v16） | 巡回はログイン後の URL を `/(app|desk)` の正規表現で待ち、巡回先は両版で通る `/app/...` を使う（version-16 は `/desk` へ転送する）。実走で両版とも確認済み |
| 版で列が違う DocType | 経路 2 の対象列 | `table_columns()` で実在する列だけ読む（2-18、2-20）。version-16 の `Module Onboarding` で確認済み |
| テストの基底クラス | `frappe.tests.IntegrationTestCase` は version-16 のみ | `lifegence_i18n/tests/__init__.py` が IntegrationTestCase → FrappeTestCase の順に解決（WP-3。同ファイルの docstring 参照） |

洗い出しに使った道具はリポジトリ外（開発者ローカルの `04_bench/workspace/acceptance/`）にある。`v16names.json` が抽出結果、`v16names_check.py` が DocType 名・項目の型・Python の API 経路を両版のベンチで照合するもの。JS の API・hooks のキー・アイコン・経路は version-15 の frappe のソースを検索して手で確認した。テストでは拾えない種類の差（アイコン名など）は、今後も version-15 の画面で目視するしかない。

## 3. 既知の制約

| 制約 | 内容 | 対処・備考 |
|---|---|---|
| 本番相当データでの精度は未確認 | 検証はローカル（デモデータ＋自作アプリ）。誤検出 0 だが、本番相当の環境で新しいパターンが出る可能性はある | 検証サイトで 1 回回して確認する |
| クリック後にしか出ない文言は対象外 | 保存時のエラー、確認ダイアログ | 経路 3（翻訳関数の未適用）が補う設計 |
| 日付選択部品の曜日 | Frappe の datepicker が日本語辞書を持たない | 翻訳ファイルでは直らない。コード側の対応 |
| 所要時間 | 1 画面 3 秒強。2,000 画面で約 1.8 時間 | 上限（0 で無制限）で調整。並列化は試作で 2.85 倍を確認（本実装は 1 プロセス） |
| v16 の翻訳供給 | Frappe 16 は PO/MO 方式で日本語を同梱しない | v16 検証サイトでの日本語供給方法を要確認 |
| 別マシン巡回で参照する「巡回マシン側」の情報 | 回る画面の一覧（対象アプリの DocType・ワークスペース）と、データと文字の見分け（マスター名、導入済みアプリ名）は巡回マシンのサイトから取る。判定の辞書だけが対象サイトのもの（2-23） | 巡回マシンは対象サイトと同じアプリ構成にする。翻訳ファイルは揃えなくてよい |
| 巡回対象の既存レコード | 各 DocType の「最初の 1 件」を開く | 権限や状態によってはフォームの一部しか見えない |
| Select の選択肢 | `select.form-control option` から UI 文字として拾う | 画面上に見えていない選択肢も対象になる（意図どおり） |
| 受入試験の件数（A-2〜A-6） | 顧客データがないと答え合わせ不可 | 合成データで機能は検証済み（`tests/`） |
